### 5.2 触发条件与频次

触发点只有三处（其余均为「到点补 / 延迟发」的时间轴兜底）：

| 触发点 | 函数 | 触发时机 |
|---|---|---|
| 提交预约成功 | `createReservation` | 落库后立即发顾客成功卡 + 管理员新预约；延迟短信（`successDelay>0`）延后 |
| 取消预约 | `cancelReservation` | 顾客取消卡 + 管理员取消提醒 + 取消短信（可由配置延迟） |
| 日历/时间轴类 | `remindReservation` | 成功短信延迟补发、前一天提醒、开场前提醒、结束提醒、取消短信补发 |

- **调度频次**：`remindReservation` 每 **15 分钟**一轮（代码文件头注释口径）。⚠️ 该定时任务是「微信开发者工具上传触发器」注册的 TCB_API 调度，用 MCP/SCF 原生定时器建会拿不到微信 token（必然 `-501001`）；本机 MCP 查 `listFunctionTriggers` 返回空属正常。⏳ **待确认**：控制台里这条 15 分钟调度当前是否处于启用状态。
- **幂等**：每类提醒都有打标字段（`smsSuccessSent` / `dayBeforeNotified` / `reminded` / `ended`），发没成功都打标，**不会 15 分钟一轮无限重试**。
- **发送时间窗**（避免深夜补发）：
  - 前一天提醒：`[dayBeforeAt, dayBeforeAt + 180 分钟]`，错过当天不补；同一顾客次日多笔**只发最早一场**。
  - 结束提醒：`[结束触发点, +120 分钟]`，超窗只打 `ended` 标记、不再发。

## 6. AI 预约：实现逻辑与限制

### 6.1 两条入口、一份核心

| 入口 | 链路 | 回复形式 |
|---|---|---|
| 小程序内 | `pages/ai/ai` → 云函数 `aiReserve` | 页面内对话气泡 + 确认卡 |
| 公众号私信 | 服务器配置 → HTTP 云函数 `mpChatHttp`（`/mp-chat`）→ 同一份 `_lib/aiCore.js` | **XML 被动回复**（文本 / 图文卡片） |

模型：`wx-server-sdk(≥4.0.2).cloud.ai()` + `hunyuan-exp` / `hunyuan-turbos-latest`（`AI_PROVIDER` / `AI_MODEL` 可覆盖）。

### 6.2 一轮对话的处理流程（`_lib/aiCore.js` → `runChat`）

```
① 每日轮次配额检查（超了直接回友好文案，不调 AI、不记日志）
② 并发：可用性摘要（30 天窗口，容器缓存 20s） + 配额 → system prompt
   system prompt 内注入：当前北京时间、今天/明天的确切日期、项目名称+项目ID+单次人数上限+可约示例
③ 调 AI，解析 JSON（{"intent":"chat|book", "reply", "slots":{...}}）
④ intent=book → resolveBooking **真实查库校验**（项目在售 → 日期在窗口 → 场次未过期未约满 → 人数）
⑤ 输出：chat（闲聊）/ ask（追问）/ confirm（确认卡）
```

### 6.3 输入约束（务必按此口径向顾客解释）

| 约束 | 行为 |
|---|---|
| 项目 | 必须是已发布未暂停的项目；名字匹配到多个时让顾客选 |
| 日期 | 只能约**今天起 30 天内**且真的排了班的日期；指定日期无场次会**先说明再给最近可约**，不会悄悄换日期 |
| 时段 | 只认排班里的开始时间；±60 分钟内自动吸附到最近场次并说明；已过开场的场次不可约 |
| 人数 | **缺失必追问**，绝不默认 1 人；取「模型抽取值 vs 顾客原话值」的**较大者**（防止被知识库里的上限口径“纠正”） |
| 人数上限 | = 项目 `maxParty`（当前两个在线项目均为 **2 人**）。超出**照约**：按上限出确认卡，并附「单次上限 N 人，已按 N 位为您安排；因系统限制，无法单次预约 N 位以上。如您特殊要求，请直接联系店铺 vx / 电话 19292757851」。**不提拆单、不推回常规预约** |
| **必填资料** | 预约必须留「**称呼（昵称）**」+「**手机号**」，**缺一不可**。顾客问「不留行不行」必须回答**不行**；并说明手机号只用于本次预约的通知。获取路径优先微信一键（称呼 `input type="nickname"` 聚焦；手机号 `getPhoneNumber` 授权），拒绝了就手工填写 —— 未在界面上填齐时，确认卡会明确提示这是必填项 |
| 追问轮次 | `AI_MAX_ASK_ROUNDS=5`，超过会引导改用常规预约 |

### 6.4 失败兜底与已知边界

- **公众号被动回复 5 秒硬死线**（自微信发出请求起算）：预算 `AI_BUDGET_MS=4000`、URL Link 生成 `LINK_TIMEOUT_MS=800`；超时那次**不写去重标记**，把机会留给微信自动重发。
- AI 报错 / 超时：**也必须回一条文本**（回 `success` = 什么都不回）；链接生成失败 ⇒ 降级为文本 + 菜单引导。
- 卡片形态下 AI 原话会被微信丢弃（图文只显示标题与描述）⇒ **所有必须让顾客看到的信息都拼进卡片 Description**（人数上限、时间调整等）。
- 落地页是**常规确认页 `pages/confirm/confirm`**（非 AI 聊天页），自带称呼/手机号/人数表单；正式版里就有，**不依赖前端发版**。
- 微信的昵称/手机号填充**必须由用户手势触发**，程序无法代授权 ⇒ AI 页与确认页都做了显眼入口；拒绝授权会明确提示「可手工填写」。

> 版本：小程序 **6.6.47**　·　云函数环境 `cloud1-d8g9mhgxm32d2eac6`
> 方案：公众号用户发消息 → **公众号服务器配置** → `mpChatHttp`（HTTP 云函数）→ 复用 AI 核心 → **XML 被动回复（文本 / 图文卡片（可带小程序码））**

## ⭐ 七期：称呼 + 手机号定为「预约必填项」（2026-09-24，已实测）

**起因（真机反馈）**：顾客问「我不留昵称和手机号，也可以提交预约吗？」→ AI 答「可以」。而实际递交必须留称呼（云端硬校验），手机号虽可选但没有手机号就发不出到店通知 ⇒ **AI 口径与实际系统行为不一致**。

**定稿口径**（用户明确指定）：

> 称呼与手机号都是预约的**必填项**，缺一项就没法下单。**手机号只会用于本次预约的通知**，顾客不用担心。

**三处同源，缺一不可**（只改一处一定会被打脸）：

| # | 落点 | 实现 |
|---|---|---|
| ① AI 口述 | `_lib/aiCore.js` system prompt **规则 14** + `_lib/kb/faq.md` 的「必填资料」条目 | 明确回答「不可以」，并主动补「手机号只用于本次预约的通知」；顾客坚持不留 → 给店铺 vx / 电话 19292757851 人工协助 |
| ② 确认卡 | `aiCore` 的 `FILL_REQUIRED_NOTE`（同时进 `confirmation.fillNote`、AI 的 `reply`、公众号卡片的 **Description**） | 卡片形态下 AI 原话会被微信丢弃 ⇒ 必填提示**必须**拼进 Description，否则顾客点进小程序才发现填不了 |
| ③ 提交校验 | 前端 `pages/ai/ai.js`（`missingProfile()` 统一判定）+ `pages/confirm/confirm.js` + 云端 `createReservation` | 缺项不再是一闪而过的 toast，而是**弹窗说明原因 + 重新拉起补全层**；云端在读取项目配置后按 `p.fields` 是否含 `phone` 判定（尊重管理端字段配置，缺省视为要） |

**引导路径**（微信限制：昵称/手机号的自动填充必须在用户手势内触发，程序无法代授权）：

1. 称呼 → `input type="nickname"` 聚焦即可「使用微信昵称」一键填入；手机号 → `button open-type="getPhoneNumber"` 一键授权（走 `getPhoneNumber` 云函数 + `cloud.openapi.phonenumber`，不需要 AppSecret）。
2. 顾客拒绝授权 / 一键失败 → **明确提示可手工填写**（如「已跳过，请在下方手工填写手机号」），入口不消失。
3. 始终没填 → 点「确认预约」会**再弹一次补全层**，并明说「这两项是必填项」。

**UI 文案同步**：AI 页确认卡与补全层的占位符改为「必填」；常规确认页 `pages/confirm/confirm` 的字段标签改为「称呼（必填）」「手机号（必填）」，引导条文案同步。

**实测**：公众号私信「我不留昵称和手机号，也可以提交预约吗？」→ 回「不行，称呼和手机号是预约的必填项，缺一项就没法下单。手机号只会用于本次预约的通知（到店提醒、时间变动等），您不用担心……」；确认卡 Description = `2026-09-25 13:30-15:00，2位。称呼与手机号是必填项，请补充完整后才能提交预约（手机号仅用于本次预约的通知）。`

## ⭐ 六期：上限文案定稿 + 相对日期「后端说了算」（2026-09-24 凌晨，已实测）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| ⑦ | 上限说明的措辞不够明确，且 `2` 有写死倾向 | 文案里"超过 2 位请…"容易让人以为是固定值 | 定稿文案：`单次上限 N 人，已按 N 位为您安排；因系统限制，无法单次预约 N 位以上。如您特殊要求，请直接联系店铺 vx / 电话 19292757851`。**两个 N 全部由项目 `maxParty` 动态拼接**（"已按 N 位"取 `capped = min(顾客说的, maxParty, 本场剩余)`） |
| ⑧ | 「今天/明天」被 AI 认成**第二天**（第 3～4 次复现） | 日期函数本身没错（`#date` 线上自检每次都对，本轮实测：`今天=2026-09-24 星期四`）；真凶是**模型输出**：弱模型更信任自己上一轮说过的话，历史里旧的错日期被反复重放 ⇒ 错误在同一条对话串里自我延续 | ① 历史只取最近 **2 小时**、且丢弃含「系统时间」的 assistant 回复（旧版泄漏话术）<br>② prompt 明令**禁止**输出"系统时间是…"、禁止自行改动今天/明天<br>③ ⭐ **硬兜底**：顾客原话里出现相对表达（今天/明天/后天/周X/N天后）时，日期**以后端 `parseDate(input)` 为准**，直接覆盖模型给的日期（仅当后端解析那天确实可约时覆盖） |

```
顾客：明天下午两点，法兰绒手冲，我们5个人
→ 卡片：2026-09-25 13:30-15:00，2位。单次上限 2 人，已按 2 位为您安排；
        因系统限制，无法单次预约 2 位以上。如您特殊要求，请直接联系店铺 vx / 电话 19292757851。
```

> 覆盖发生时函数会打日志 `[aiCore] 日期纠正：模型给 X，顾客原话「…」解析为 Y`，排障时可直接搜。

## ⭐ 零之前·五期：资料前置 + 人数上限口径修正（2026-09-23 夜，已实测）

四期上线后再真机复测，又暴露两件事。**全部随云函数部署生效；其中资料弹层的前端部分需要体验版。**

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| ⑤ | AI 预约时不主动要昵称/手机号，等谈妥才要，顾客卡在"提交不了" | 确认卡虽有输入框，但**没有前置索取**；微信的昵称/手机号填充又**必须在用户手势内触发**，无法自动弹 | 进入 AI 页即弹「资料补全层」（称呼 `type="nickname"` + `open-type="getPhoneNumber"` 一键取号）；点「确认预约」时若仍缺，**再弹一次**；拒绝授权明确提示"可手工填写" |
| ⑥ | 人数超上限就**不预约**了，还引导去「常规预约」；且提示"按上限约还是**拆单**" | `resolveBooking` 超上限返回 `ok:false` 反复追问 → 多轮后撞 `AI_MAX_ASK_ROUNDS` 被推去常规预约 | **超上限照约**：按上限钳制后直接给确认卡；话术只讲"上限就是 N 人 + 人工出口"，**不提拆单、不推回常规预约** |

### ⑤ 资料前置的两处入口

```
进入 AI 对话页（pages/ai/ai）
   └─ 若 users 里缺称呼或手机号 → 立即弹「资料补全层」
        ├─ 称呼输入框（type="nickname"，聚焦时微信提供「使用微信昵称」一键填入）
        ├─ 手机号输入框 + 「一键获取」按钮（open-type="getPhoneNumber" → 云端 cloud.openapi 换号）
        ├─ 「填好了」→ 关闭；若本层是点确认时弹出的，直接接上提交，少点一次
        └─ 「稍后再说，先聊聊」/ 拒绝授权 → 明确提示「可手工填写」，不阻断

公众号卡片落地页（pages/confirm/confirm）
   └─ 资料不全 → 顶部亮出「还差一步就能确认」引导条，「获取手机号」按钮同时切成主色填充
```

> ⚠️ 微信的昵称/手机号**必须由用户手势触发**，程序无法代授权 —— 所以能做到的极限就是"把入口做显眼 + 说清为什么要"，而不是"自动弹窗"。

**拒绝授权不再静默返回**（旧代码 `if (errMsg !== 'ok') return` 什么都不提示，顾客以为按钮坏了）：

| 情形 | 提示 |
|---|---|
| 用户点了拒绝 | 「已跳过，请在下方手工填写手机号」 |
| 其他失败 | 「未能获取，请手工填写手机号」 |
| 提交时仍缺称呼 | 弹窗说明"称呼必填、可就地手工输入；手机号可一键或手工" |

### ⑥ 人数上限的三个关键决定

**1）上限口径 = 项目配置的 `maxParty`，它就是上限本身。**

```
顾客说 5 位、项目上限 2 位
  ❌ 旧：ok:false →「需要我按 2 位帮您约，还是拆成两单？」→ 反复追问 → 多轮后推去常规预约
  ✅ 新：ok:true  → 直接给 2 位确认卡 + 一句话说明（六期定稿）
     「单次上限 2 人，已按 2 位为您安排；因系统限制，无法单次预约 2 位以上。如您特殊要求，请直接联系店铺 vx / 电话 19292757851」
     ※ 文案里的两个「2」都是 `${maxP}` 动态拼接的，跟随项目配置
```

**2）必须从用户原话做确定性解析，且取「模型值 vs 原话值」的较大者。**

知识库里写着「单次预约上限 2 人」，模型会拿这个口径去**纠正顾客**：顾客说"5 个人"，模型把 `slots.partySize` 填成 2。只信模型值 ⇒ 永远触发不了超限提示，顾客拿到 2 人位卡片却不知道自己说的 5 位被静默改小了（线上复现）。

> ⚠️ 这里还抓到一个**上一轮修复的漏传**：`resolveBooking(slots, ctxProjectId)` 一直没传第三个参数 `input`，导致"从原话解析人数"的代码**形同虚设**。现已修好，并加了本地桩回归。

**3）卡片形态下 `reply` 会被丢弃 —— 说明必须写进卡片 `Description`。**

图文消息只显示 `Title` / `Description`，AI 的原话（`reply`，含上限说明）不会展示。所以 `confirmCard()` 现在把 `confirmation.note` 拼进描述：

```
预约确认 · 法兰绒手冲咖啡预约
2026-09-25 13:30-15:00，2位。单次上限 2 人，已按 2 位为您安排；因系统限制，无法单次预约 2 位以上。如您特殊要求，请直接联系店铺 vx / 电话 19292757851。点击进入小程序即可完成预约。
```

### ⚠️ 顺带修掉一个隐藏的「永远收不到回复」根因

MsgId 去重原来**只认 openid 就判重**，而 user 轮次是在调 AI **之前**落库的。后果：

```
冷启动超时（>5s）→ 微信没收到回复 → 微信重发同一条（同一 MsgId）
   → 被判「重复」→ return 'success'（什么都不回）→ 用户永远收不到，且静默失败
```

改为**只认 `role:'assistant'` 且带该 MsgId 的记录** = "这条消息是否被成功回复过"；并且**只在回复耗时 < 4600ms（很可能被微信接收）时才写去重标记**，超窗那次不写，把机会留给重发（重发时 URL Link 已进容器缓存、AI 也热了）。

配套把预算放宽：`AI_BUDGET_MS` 3600 → **4000**，URL Link 生成加 **800ms 硬超时**（最坏 4.8s，不越 5 秒死线；被砍掉就回落文本 + 菜单引导，不会更差）。

### 为什么落地页要从 AI 对话页换成常规确认页

```
❌ 旧：点卡片 → pages/ai/ai（对话页）      → 旁边只有一个「确认预约」按钮，称呼/手机号无处可填
✅ 新：点卡片 → pages/confirm/confirm      → 项目/日期/时段/剩余名额 + 称呼 + 手机号 + 获取手机号按钮
                                             + 人数步进器（标着「单次最多 N 人」）→ 直接提交
```

`pages/confirm/confirm` 是常规预约链路里**早就存在且已在正式版发布**的页面，所以：
- 顾客点卡片**一步到位看到确认表单**，不用重走对话；
- 该修复在线上**立刻生效**，不必等小程序新版本审核。

### 新增两条排障命令（公众号私聊秒回，不走 AI）

| 命令 | 作用 | 怎么读 |
|---|---|---|
| `#date` | 打印**真实的**北京时间 / 今天明天后天 / 短语解析 / 人数解析 | `今天` 与 `星期` 对不上 = 又出现时区平移 |
| `#oa` | 用**真实可约场次**拼一条与卡片同款的链接，点它可验落地页 | 点进去若能看到该项目/日期/时段的确认表单 = 落地链路通 |

### ⚠️ URL Link 会落到哪个小程序版本？

`generate_urllink` 的 `env_version` 决定用户打开的是**线上正式版 / 体验版 / 开发版**。
若线上正式版还没有某个新页面能力，链接就会"看起来没生效"。现在已抽成 `wxaEnvVersion()`：
- 默认 `release`（**对真实顾客这是唯一正确值**）；
- 需要先拿体验版验证时：给 `mpChatHttp` 加环境变量 `WXA_ENV_VERSION=trial`，验证完记得改回。

## ⭐ 零之前·卡片与一键直达小程序（2026-09-23 二期）

**问题**：一期只能回纯文本 —— 用户收到回复了，但**点不到任何链接、也拿不到小程序卡片**。

**根因**：被动回复本身只支持 text/image/voice/video/music/news。想给「小程序卡片」得走服务号客服消息
（`message/custom/send` + `miniprogrampage`），而服务号 `access_token` 被 **IP 白名单**拦死（云函数出口 IP 每次漂移 → 恒 `40164`）。

**突破**：实测发现 **IP 白名单只对服务号生效，小程序没有这道墙**。

| 探测（真实 AppID + 故意错的 secret，3 轮） | 结果 | 判读 |
|---|---|---|
| **小程序** `cgi-bin/token`（`wxb97578ed89c6e2c7`） | `40125 invalid appsecret` | ✅ **IP 未校验，通路 OK** |
| 服务号 `cgi-bin/token`（`wx4d8d957ee8af6073`） | `40164`（出口 IP `123.207.222.208`/`175.24.202.117`/`118.25.69.217`） | ❌ 被拦 |
| 服务号 `sns/oauth2/access_token`（对照） | `40029 invalid code` | 通路 OK |

> 判据（本项目踩过两次）：**只有 `40164` 代表 IP 被拦**；`40001`/`40125` 说明请求已越过 IP 校验、只是凭证不对；
> `40013` 是 AppID 非法的假阴性，不能用来判断 IP。

**因此**：用**小程序**身份调 `wxa/generate_urllink` 生成 `https://wxaurl.cn/xxx`，塞进被动回复的
**图文消息(news)** 卡片 `<Url>` —— 用户在微信里点一下直接唤起小程序，且 `path/query` 支持带参。

**最终形态（确认场景）**：

```
┌─────────────────────────────┐
│ [配图]  预约确认 · 法兰绒深烘咖啡  │
│  2026-09-24 14:00-15:30，2位。 │  ← 点整张卡片
│  点击进入小程序即可完成预约。      │     → 直达小程序确认页（带参 + log 回写漏斗）
└─────────────────────────────┘
```

**降级顺序**：URL Link 成功 → 图文卡片；失败或超 5s 预算 → 文本 + 菜单引导（不会没回复）。

## ⭐ 零之前·能不能「直接发一张小程序码」？（2026-09-23 三期）

**结论**：能，但免费的上限是「**图文卡片的封面图就是二维码**」；**真正的独立图片消息（大图）做不到**。

| 形态 | 可行性 | 原因 |
|---|---|---|
| 被动回复 `image` 消息 | ❌ | `MediaId` 只能由**公众号素材接口**上传获得，而该接口要服务号 `access_token` → 被 IP 白名单拦死 |
| 客服消息 `image` / 小程序卡片 | ❌ | 同上（都要服务号 token） |
| 图文消息(news) 的 `PicUrl` | ✅ | `PicUrl` 接受**任意公网图片链接**，完全不需要微信素材接口 |
| 文本里附图片链接 | ✅ | 最简，但用户要多点一次 |

**实现链路（2026-09-23 14:10 定稿，已全链路实测通过）**：
小程序身份生成小程序码（`wxa/getwxacodeunlimit`，scene=`oa`、page=`pages/ai/ai`）→ 用 Pillow **烘焙进品牌卡片**（`deploy/wxa-qr.py`）→ 上传**静态托管** `oa/card-qr.jpg` → 填进 `PicUrl`。

为什么用「静态托管的成品图」而不是请求时实时生成：

| 方案 | 链接性质 | 耗时 | 结论 |
|---|---|---|---|
| 请求时实时生成 → 云存储 | **临时签名链接**（`?sign=&t=`，2h 过期）→ 老卡片变裂图 | 生成+上传+换链接 ≈ +1.2s | ❌ 弃用（降级为 `#qrgen` 诊断） |
| 预先烘焙 → 静态托管 | **永久公网链接** | 0 次额外网络往返 | ✅ 采用 |

入口二维码是**通用**的（不因人而异），一次烘焙终身可用。卡片 `<Url>` 仍用 URL Link，所以**点整张卡片**照样能带参直达小程序确认页，二维码多给一条「长按识别」的路。

> 改图注意：`OA_CARD_PIC` 默认已指向这张带码的成品图。换成别的图会**同时丢掉二维码**，改之前请用 `deploy/wxa-qr.py` 重新合成。

### 自检命令（公众号里私聊发送，秒回诊断，不用走完整个预约对话）

|---|---|---|

### ⚠️ URL Link 参数坑（实测，别踩）

`wxa/generate_urllink` 的三个时间参数里，**只有「永久链接」稳过**：

⇒ 代码固定用 `is_expire: false`。返回域名可能是 `wxaurl.cn` 或 `wxmpurl.cn`，两者都合法。

| 日志 | 含义 |
|---|---|
| `POST msgType=text from=oXXXX sign=ok` | ✅ 消息进来了，配置没问题 |
| `被动回复耗时=xxxxms intent=confirm` | ✅ 回复已生成；**看这个 ms 数** |
| `重复 MsgId，跳过` | ⚠️ 微信没接受首次回复（超时）→ 就是踩到 5 秒线了 |

**耗时怎么量**：响应头 `x-cloudbase-upstream-timecost`（单位 ms）直接给出函数真实耗时。
微信 5 秒预算里要装下：网关往返 + 所有 DB 操作 + AI 调用。

## 零、IP 白名单的取舍（决定「能不能发小程序卡片」）

### 先说结论：mpChat 现在有三条回复通道，白名单只影响「能不能用卡片」

| 通道 | 原理 | 是否受 IP 白名单影响 | 能否发小程序卡片 |
|---|---|---|---|
| ① 客服消息直连 | 云函数 HTTPS 直连 `api.weixin.qq.com` | ❌ **受影响**（40164） | ✅ 能 |
| ② 云调用 `openapi` | 微信内网转发 | ✅ 不受影响 | ✅ 能（待真机验证） |
| ③ **被动回复** | 云函数 `return` 消息对象，官方通道转换 | ✅ 不受影响 | ❌ 只能纯文本 |

**现已实现自动降级：①失败 → 试② → 都失败走③。所以无论白名单是什么状态，用户都一定能收到回复。** 白名单只决定「是否能在回复里附上小程序卡片」。

## 四、已知限制（务必知悉）

1. **IP 白名单 → 决定能否用卡片，不决定能否回复**：`mpChat` 已实现「客服消息直连 → 云调用 openapi → 被动回复」三级自动降级/IP 白名单为空则全程走直连（有卡片）；非空则回落被动回复（纯文本）。详见第零节。
   - 排障判据：请求微信返回 **40164** = IP 未放行；**40001/40125** = IP 已放行、凭证问题；**40013** = AppID 错。
   - ⚠️ 诊断陷阱：用假 AppID/假 token 探测会得到 40013/40001，**不能**证明 IP 已放行——只有用真实 AppID 测到 40001 才算通过。
2. **48 小时 / 5 条额度**：仅约束通道 ①客服消息（②云调用同理）；通道 ③被动回复不受额度限制。
3. **必须回小程序下单**：公众号拿不到手机号、弹不了订阅授权，所以预约一律通过卡片导回小程序完成。
   - 通道 ①③可用时（有卡片/文字链）：直接跳转小程序确认页。
   - 退到纯文本时：回复末尾追加「点击底部菜单进入小程序」引导，靠已配好的公众号菜单跳转。
4. **卡片只能跳线上版**：开发版小程序点不开卡片链接。
5. **AI 超时**：`mpChat` 已设 60 秒超时；若混元响应慢，用户会晚几秒才收到回复（异步客服消息，不占用 5 秒被动回复窗口）。

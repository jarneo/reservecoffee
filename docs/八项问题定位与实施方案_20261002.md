## 二、问题 1 · 首页菜单两列错位

### 根因（已复核）

`miniprogram/pages/index/index.js:14-18`

```js
function splitCols(list) {
  const colA = [], colB = []
  ;(list || []).forEach((it, i) => { (i % 2 === 0 ? colA : colB).push(it) })
  return { colA, colB }
}
```

**按索引奇偶硬分，不看高度。** `MENU_LIMIT = 15`（`getHomepage:5`），15 项时左 8 / 右 7 → 底边差 = 一整张图高度（你观察到的现象）。

叠加放大：

- `index.wxml:34,46` 图片 `mode="widthFix"` → 高度按原图比例，每张不同
- `index.wxss:31` `.menu-cols{align-items:flex-start}` → 两列独立堆叠，永不锁行
- `index.wxss:36` `.menu-img{height:auto}` → 无固定高度约束

**已排除**：字符串比较排序（排序在 DB 侧）、NaN（`saveProduct:25` 用 `Number.isFinite` 兜底）、grid/absolute/nth-child（样式只有 flex）、本地兜底常量。

### 方案：真·瀑布流（按预估高度贪心分列）

**核心**：每张卡片按 `ratio` 算预估高度，每次把卡片放进**当前较矮的那一列**。差值被持续摊平，底边自然齐平。

**新建 `miniprogram/utils/masonry.js`**

```js
// 首页菜单双列瀑布流：按预估高度贪心分列（总是给当前较矮的一列）
// 高度预估 = 列宽 / 图片宽高比 + 固定文字区高度
// ⚠️ ratio 缺失（存量未重传图）时用 DEFAULT_RATIO 兜底，误差表现为该卡略高/略低
const DEFAULT_RATIO = 1.30   // 菜品图多为竖构图，取 1.30 而非 1.0
const FIXED_RPX   = 72       // 边框2 + info padding 16*2 + name 行高 38
const COL_W_RPX   = 343      // (750 - 页面 padding 24*2 - gap 16) / 2，与 index.wxss 对齐

function cardHeightRpx(item) {
  const r = Number(item && item.ratio)
  const ratio = (isFinite(r) && r > 0.2 && r < 5) ? r : DEFAULT_RATIO
  return Math.round(COL_W_RPX / ratio) + FIXED_RPX
}

function splitMasonry(list) {
  const colA = [], colB = []
  let hA = 0, hB = 0
  ;(list || []).forEach(it => {
    const h = cardHeightRpx(it)
    if (hA <= hB) { colA.push(it); hA += h } else { colB.push(it); hB += h }
  })
  return { colA, colB, heightA: hA, heightB: hB }
}
module.exports = { splitMasonry, cardHeightRpx, COL_W_RPX, DEFAULT_RATIO }
```

**`ratio` 字段全链路**（products 集合**只增不改，不影响存量数据**）：

| # | 位置 | 改动 |
| --- | --- | --- |
| 1 | `menuAdmin.js` 上传处 | `wx.getImageInfo` 取 width/height → 存 `imageRatio` |
| 2 | `saveProduct/index.js` patch | 白名单加 `ratio`（`Number`，只接受 0.2–5，越界归 0） |
| 3 | ⚠️ `getHomepage/index.js:159-164` | **显式字段投影**，必须加 `ratio` |
| 4 | `listProducts/index.js:14` / `getMenu` / `adminProducts` | 用 `{ ...p }` 展开，**自动带过，无需改** |


> 复核确认：`getHomepage:159-164` 的投影为
> `_id, name, price, desc, image, categoryId, imageUrl, reviewCount` —— 确实不含 `ratio`，必须显式加。

**3 个调用点全换**（含 menu 页的同一套逻辑）：

- `index.js:110` renderHomepage
- `index.js:143` onCatChange → 'all'
- `index.js:152` onCatChange → 具体分类

**同步必改**：

- **单测** `tests/masonry.test.js`：空数组 / 单项 / 15 项均衡（断言 `|heightA-heightB| ≤ 单卡高度`）/ ratio 非法兜底

### 预期效果与残余风险

| 指标 | 现在 | 改后 |
| --- | --- | --- |
| 底边偏差 | 一整张图高度 | **≤ 一张卡高度**（贪心保证） |
| 预估误差 | — | ratio 正确的卡 ≈ 0；缺失的卡有偏差 |

## 五、问题 4 · 图片模糊

**根因：双重有损压缩。** 4 处 `wx.chooseMedia({ sizeType: ['compressed'] })` 先压一次（微信压 q≈70、长边限 1080，算法不可控），`img.compress` 再压一次。JPEG 两次有损**非线性叠加**。
叠加 `SPEC.card = 400w/q72` —— 这是 imageMogr2 时代按「每栏 170px 逻辑宽」定的，3x 屏实际需 510 物理像素。
CDN 侧已彻底停用（`_lib/index.js:856` `ENABLE_CI_THUMB = false`，已核验全部 74 个副本）。
**原图已被覆盖，不可恢复 —— 存量图只能重传。**

### 1. 消除双重压缩（主因）

| 文件 | 行 |
| --- | --- |
| `menuAdmin.js` | 67 |
| `cover.js` | 39 |
| `projectConfig.js` | 124 / 146 / 223 |


全部 `sizeType: ['compressed']` → `['original']`。

### 2. SPEC 量化调优

```js
// 档位按「实际显示物理像素」定。3x 屏菜品栏 343rpx ≈ 178 逻辑px ≈ 535 物理px
const SPEC = {
  hero:   { width: 1080, quality: 80 },  // 全宽 750rpx，3x 需 1080
  cover:  { width: 1080, quality: 80 },
  card:   { width: 640,  quality: 80 },  // 3x 需 535 → 取 640，留 20% 余量
  icon:   { width: 240,  quality: 82 },  // 3x 需 273，图标小且方形，略欠可接受
  avatar: { width: 240,  quality: 82 },
  full:   { width: 1280, quality: 82 }   // 预留，本期不启用
}
```

体积估算（原图 3000×4000，JPEG q80）：card 13KB → 38KB；hero 47KB → 109KB。hero 偏大但只有 1 张，首图是门面。

**为什么不启用 `full` 档**：需改 schema（`saveProduct:21` 只存一个 `image` 字段）+ 3 处下发 + 存储与上行双倍；而**存量数据没有高清源**，`imageFull` 上线即空表，反而制造「有的有有的没有」。新 `card 640` 已是旧 400 的 2.56 倍像素，改善已明显。
将来若要高清，正确路径是把 `card` 提到 1080（一份图服务两处），不是加第二份文件。

### 3. `img.js` fail 分支加 warn

`compressedWidth` 只约束宽度不约束高度 → 极端长图（1080×20000）输出超 iOS 单边上限会 fail → **回退原图，3~5MB 直传且无任何提示**。加一条 `console.warn`（成本最低、可观测性最高）。不加体积硬限制（会阻断用户，违反 `img.js:4` 的设计原则）。

### 4. 存量图：打标记引导重传

原图永久丢失，修复只对**新上传**生效。不做批量重传（小程序无「批量选图」原生能力，15 张 = 15 次弹窗，比手动重传更累）。
`menuAdmin` 菜品行对 `!Number(p.ratio)` 的加「建议重传」标签 + 编辑弹层提示。
**这与问题 1 的 `ratio` 是同一套机制** → `menuAdmin` 一次编辑同时做两件事。

**样式核对**：`design/second-design.html` / `menu-design.html` / `menu-category-prototype.html` 均**不含** `.menu-cols`/`.menu-card` 字样，本期不改 wxss → **无需反向同步**。

```js
// 首个进入者自动成为 owner
// ⚠️ 仅当 admins 集合为空（全新环境）时授予；集合非空但无 owner 说明数据异常，
//    此时自动授予等于把店主权限送给任意顾客 —— 改为拒绝并告警，由人工修数据。
async function ensureOwner(openid) {
  if (!openid) return null
  const any = await db.collection(COL.admins).limit(1).get()
  if (any.data.length) return null                       // 集合非空 → 绝不授予
  await db.collection(COL.admins).add({
    data: { openid, role: 'owner', note: '初始店主', inviterOpenid: '', createdAt: Date.now() }
  })
  return 'owner'
}
```

**兼容性**：只影响「集合非空但无 owner」这一异常态。若当前环境有 owner → **行为完全不变**。
**上线动作**：MCP 查 `admins` 确认至少 1 条 `role:'owner'`，再查 `getRole` 日志有无 warn。

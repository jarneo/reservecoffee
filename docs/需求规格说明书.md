## 0. 文档目的与范围

本 SRS 定义**顾客侧**「资料获取 + 预约信息填写」的需求，覆盖两条主链路：

1. **微信昵称 / 头像**在**首次进入小程序**时合规带出并落库；
2. **手机号**在**预约确认页**经用户显式授权（`getPhoneNumber`）解密，或手动填写。

两个字段均**允许手动覆盖**，授权/带出结果仅作预填、不强制。

> ⚠️ **范围外**：本 SRS 不重定义管理端配置、场次、截止规则等（见设计文档 §2/§14）。仅新增 `users` 集合与少量顾客端/云函数改动。

---

## 1. 目标流程（用户视角）

1. **登录 / 首次进入小程序**：自动带出顾客的**微信昵称**作为默认称呼，写入"我的"资料（可改、可跳过）。
2. **预约确认页**：提供**「授权手机号」**一键获取（用户点一次），也可手动填写。
3. 两个字段（称呼 / 手机号）在任何环节都**允许手动输入**，授权/带出结果只是预填，不强制。

---

## 2. 功能需求

- **FR-1 登录获取微信名**：顾客首次进入小程序时，系统取得其微信昵称作为默认称呼，与 `openid` 绑定存入 `users` 集合；后续进入与预约直接复用，用户可随时修改。
- **FR-2 预约授权手机号**：确认预约页提供"授权手机号"按钮（`getPhoneNumber`），用户点一次即由服务端解密为真实号码；未授权时可手填。
- **FR-3 均可手填**：称呼与手机号均保留普通输入框，授权/带出仅作预填，用户可覆盖。
- **FR-4 资料持久化**：以 `openid` 为主键建 `users` 集合，存 `{openid, name, phone, avatar, updatedAt}`；写=仅云函数。实现设计文档 §6.1 提出的"首次登录资料"诉求。

---

## 3. 平台约束与合规实现（务必写入，避免需求失真）

> ⚠️ **微信不允许"登录即静默获取昵称"**。自 2022 年起 `getUserProfile`/`getUserInfo` 已收回真实资料返回能力；任何小程序**无法在启动时自动读到用户的微信昵称**。昵称只能在用户主动触发的场景下带出。因此 FR-1 的"登录获取"需按下述合规方式落地：

- **昵称（FR-1 合规等价）**：在顾客**首次进入首页时**弹一个轻量"完善资料"引导卡，内部用 `<input type="nickname">`（聚焦即弹出"使用微信昵称"气泡，点一下带入）+ `button open-type="chooseAvatar"`（头像）；用户点一下即完成"登录获取昵称"的体验，可跳过。取到后写入 `users` 集合。**这不是静默读取，是首次进入时的一次用户点选**，但对外体验等同于"登录就拿到了微信名"。
- **手机号（FR-2）**：必须 `getPhoneNumber` 用户显式授权，无静默途径——与你的设想一致。
- **微信号字段**：微信**永不**向第三方开放，若项目 `fields` 含 `wechat`，只能手填，文档需标注"不可自动带出"。

## 4. 影响面（供开发评估）

- **前端**：
  - 新增/复用「首次资料引导卡」（首页 `pages/index` 或独立轻页）；内部 `<input type="nickname">` + `button open-type="chooseAvatar"`。
  - `pages/confirm`：保留手机号授权按钮；将"前端拿明文 phone 直传"改为**上送 `phoneCode`**，由 `createReservation` 服务端 `cloud.getPhoneNumber` 解密（见 §6 现状）。
- **云函数**：
  - 新增 `getMyProfile` / `saveProfile`（读写 `users` 集合）。
  - `createReservation` 增加 `phoneCode` 解密分支（`cloud.getPhoneNumber`）；成功解密后写入 `users.phone` 并用于本次预约。
- **数据库**：新建 `users` 集合（权限：读=仅云函数，与现有集合一致）。

## 5. 验收要点（概览）

- [ ] 新顾客首次进首页出现资料引导，点选即带出微信昵称/头像，可跳过、可改；
- [ ] 该昵称在「我的」与预约确认页自动预填；
- [ ] 预约确认页「授权手机号」点一次即填入真实号码，拒绝/失败时可手填且不阻断；
- [ ] 全程**无"启动即弹窗强索昵称/手机"**的违规行为；
- [ ] 顾客资料按 `openid` 正确落 `users` 集合，二次预约免重填。

## 附录 A：源码校正过的数据模型（as-built，引用设计文档 §14.6）

> 以下为项目**实际落地**的数据模型（非设计文档 §9 的"建议嵌套结构"）。`projects` 为扁平顶层字段。新增 `users` 集合见附录 B。

### A.1 `projects` 文档顶层字段清单（v1.7 实际）

- 基础：`name, icon, image, intro`
- 发布 / 预约态：`published`(bool), `paused`(bool)
- 规则：`needReview, dailyLimit, advanceDays, useSlotTemplate, slotTemplate[], introImages[], openDays[]`
- 短信：`smsEnabled, smsNotice`
- 本轮相关：无（昵称/手机不落在 projects，独立存 `users`）
- 时间戳：`createdAt, updatedAt, ownerOpenid`

状态表达（三标记组合，非单字段）：`published`（首页可见）/ `paused`（是否接单）/ `deleted`（软删）；四态徽标：已发布 / 未发布 / 暂停预约 / 已删除。

### A.2 `reservations` 文档（现状，供对齐）

当前 `createReservation` 接收并落库：`{ projectId, date, sessionId, name, phone, partySize, note, openid, status, createdAt, ... }`。
`name` / `phone` 当前为顾客在 `confirm` 页手填或授权后直传明文。**改造后**：`phone` 改由 `phoneCode` 服务端解密得到；`name` 默认预填 `users.name`，可被本次输入覆盖。

## 附录 B：新增 `users` 集合设计（FR-4）

> 权限：读=仅云函数（与 `projects`/`reservations` 一致）；写=仅云函数（`saveProfile` / `createReservation` 内部）。

```
{
  _id: <openid>,                 // 以 openid 作主键（与微信登录态天然一一对应）
  openid: string,                // 冗余存一份，便于索引/查询
  name: string,                  // 微信昵称（合规带出）或用户手填，可改
  phone: string,                 // 授权解密的真实号码或手填，可改
  avatar: string,                // chooseAvatar 返回的本地/云文件地址（可选）
  updatedAt: number              // 毫秒时间戳
}
```

- **读写入口**：`getMyProfile(openid)` 读取；`saveProfile(openid, {name?, phone?, avatar?})` 增量更新（`db.command.set` 合并，不覆盖未传字段）；`createReservation` 在解密 `phoneCode` 成功后顺带 `saveProfile` 落 phone。
- **首次进入**：引导卡点选 → 前端调用 `saveProfile` 写入 name/avatar；跳过则不写，后续任一时点可补。
- **隐私**：`phone` 仅服务端可见，前端只回显脱敏或本机缓存，不暴露明文给非授权页。

## 一句话总结差异

你想要的体验（登录拿昵称、预约授手机、都能手填）完全可行；唯一要纠偏的是——"登录拿昵称"在微信里必须做成**首次进入时点一下带出**，而不是后台静默读取。本文第 3 节就是为这点留的合规说明，建议原样保留，免得开发按字面去调一个不存在的"静默获取昵称"接口。

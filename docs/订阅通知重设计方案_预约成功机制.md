> 整合前几轮沟通，形成可评审的单一事实来源。本版核心变更：
> 1. 预约成功改为「**微信订阅优先 + 短信保底 + 客户端弹窗**」三件套（此前被错误地从弹窗移除）。

## 1. 需求描述

### 1.1 背景与目标
- 每次预约成功都会占用一个时间段（session slot）。系统须依据该时间点的时间轴，在**不同节点触发内容各异的提醒**，确保顾客不错过「留座确认 / 前一天 / 开场 / 结束」。
- 预约成功是顾客最关心的节点，必须**可靠触达**，且体验友好（不当即弹两次窗）。

### 1.2 通知类型全集（顾客端共 5 类）
| # | 类型 | key | 是否由时间轴推导 |
|---|------|-----|:---:|
| 1 | 预约成功 | `reserveSuccess` | 否（提交/审核事件） |
| 2 | 前一天提醒 | `dayBefore` | 是 |
| 3 | 开场前提醒 | `reminder` | 是 |
| 4 | 结束提醒 | `reminderEnd` | 是 |
| 5 | 取消提醒 | `reserveCancel` | 否（取消事件） |

> 注：需审核项目，审核通过时发送「预约成功」(同一 `reserveSuccess` 模板)，不另立第 6 类。现有代码已如此实现。

### 1.3 三层送达模型（核心）
| 层 | 通道 | 必要条件 | 角色 |
|---|---|---|---|
| ① | 应用内提交成功页 / 弹窗 | 无 | **必达保底**（预约成功确认 UI） |
| ② | 微信订阅消息 | 用户弹窗授权 | 主推送（富卡片，优先级最高） |
| ③ | 短信 | 全局开关 + 短信项目设置开启 + 微信未送达 | **兜底**（微信失败/未授权时补发） |

→ 即便顾客**拒绝全部订阅授权**，预约成功仍有 ① 应用内页；若开启短信，取消/提醒仍有 ③ 短信，不会出现「完全收不到」。

### 1.4 预约成功专项需求（本版明确）
针对「预约成功」一项，三条并列要求：
1. **优先微信订阅消息**：经 `wx.requestSubscribeMessage` 授权后，由 `createReservation` 在提交（或审核通过）时经微信服务通知下发。
2. **短信保底**：当微信未送达（未授权 43101 / 字段非法 / 凭证异常）时，按现有 `shouldSkipSms` 逻辑补发短信，确保触达。
3. **客户端弹窗提示**：提交后弹出微信授权窗（申请预约成功模板）；同时展示应用内「提交成功页」作为必达确认。

### 1.5 时间轴差异化提醒需求
依据预约占用的 session slot，在以下节点触发差异化提醒（内容/字段各不相同）：
- **前一天**：`dayBeforeAt`（线上配置 = `21:20`）起窗口内触发。
- **开场前**：`sessionStart` 前 `approachingOffset` 分钟（默认 60）触发。
- **结束**：`sessionEnd` 触发（或 `expiredWhen=after` 时 +`expiredOffset`）。
- 仅当该节点**仍在未来**时才申请其授权（过去节点无法再弹窗授权，自然跳过）。

## 2. 现状核对（代码事实，避免凭空设计）

| 事实 | 位置 | 结论 |
|---|---|---|
| 微信单次最多 3 个 tmplId，超量整体失败（20003）；分批会脱离手势上下文导致第 2 组失败 | `miniprogram/utils/util.js:55-71` | 提交弹窗必须控制在 **≤3 个模板 / 1 次弹窗** |
| `notifyPlanOf` 恒含 `reserveSuccess:true`，再按优先级 `reserveSuccess>dayBefore>reminder>reminderEnd` 截断 ≤3 | `miniprogram/utils/subscribe.js:133-159` | **远期单会把 `reminderEnd` 静默置 false** → 结束提醒永远不申请授权 → 只能短信兜底（偏差，待修） |
| `createReservation` 发预约成功条件：`!needReview && plannedOf(plan,'reserveSuccess') && subOn && subbedOf(userSubs,'reserveSuccess')` | `cloudfunctions/createReservation/index.js:165` | 已支持微信优先；前提是弹窗先授权 |
| `shouldSkipSms`：`skipSmsIfWxOk && wxRes.ok` 才跳过短信，否则短信兜底 | `cloudfunctions/_lib/index.js:283` | 短信保底机制已存在，直接复用 |
| `confirm.js` 提交时 `requestNotify()` → `tmplIdsOfPlan(plan, null)` | `miniprogram/pages/confirm/confirm.js:129-131` | 当前已把 plan 内模板一次性申请（含预约成功） |

**结论**：「预约成功=微信优先+短信保底+弹窗」当前**已部分成立**；真正要改的是①去掉静默丢结束提醒的硬截断、②把授权槽分配做成显式策略、③取消提醒移出提交弹窗避免超 3。

## 3. 设计方案

### 3.1 触发时机与送达矩阵
| # | 类型 | 触发时机 | 触发方式 | 送达方式 | 授权申请位置 |
|---|------|---------|---------|---------|------|
| 1 | 预约成功 | 免审=提交瞬间；需审核=审核通过 | 提交/审核事件 | ①应用内成功页(必达) ②微信订阅(优先) ③短信(保底) | **提交弹窗**（必含） |
| 2 | 前一天提醒 | `dayBeforeAt` 窗口 | 时间轴定时 | ②微信 ③短信 | 提交弹窗（节点在未来才申请） |
| 3 | 开场前提醒 | 开场前 `approachingOffset` 分 | 时间轴定时 | ②微信 ③短信 | 提交弹窗（节点在未来才申请） |
| 4 | 结束提醒 | `sessionEnd` | 时间轴定时 | ②微信 ③短信 | 提交弹窗（节点在未来才申请） |
| 5 | 取消提醒 | 取消事件 | 取消事件 | ②微信 ③短信 | 设置页/预约详情页授权为主；提交弹窗有空位时（③/④档）顺带申请 |

### 3.2 授权 / 弹窗策略（核心 · 解决「不要两次弹窗」）
**原则：提交时只弹 1 次微信授权窗，窗内模板 ≤3。**

授权集 = `[预约成功]` ∪ `{仍在未来的时间轴提醒}`，再按「预约成功必占 1 槽 + 时间轴最多 2 槽（优先级 前一天>开场前>结束）」分配。
时间轴提醒是否「仍在未来」由 `notifyPlanOf` 的窗口判定（与现有逻辑一致）：`dayBefore` 要求 `now < 前一天窗口末`；`reminder` 要求 `now < 开场前窗口(=开场−offset)`；`reminderEnd` 要求 `now < 结束窗口`。**即「开场前」在预约时若已错过（如当天临近开场才下单），不会被申请也不会被发送——不会推过期提醒。**

按提交时刻 `now` 相对时间轴的三个关键节点（前一天窗口末 / 开场前窗口 `sessionStart−offset` / 场次结束 `sessionEnd`）判定，实际分四档（示例以默认 offset=60 分钟、dayBeforeAt=21:20 计）：

| 档位 | 条件（提交时刻 `now` 相对时间轴） | 提交弹窗授权集（≤3） | 说明 |
|---|---|---|---|
| ① 远期单 | `now < 前一天窗口末`（距开场 >1 天） | `[预约成功, 前一天, 开场前]` | 时间轴 3 项超槽，按优先级截前 2 项；`结束提醒` 不进微信授权集 → 走 ③短信兜底 / 设置页补授权（你此前确认采纳 A） |
| ② 当天早单 | 前一天窗口已过，但 `now < 开场前窗口` | `[预约成功, 开场前, 结束]` | 时间轴恰 2 项（开场前+结束），全部拿到微信授权（占满 3 槽，无空位） |
| ③ 迟到单（开场已过·场次未结束） | `开场前窗口 ≤ now < sessionEnd`（过了开场时间仍可约、但场次尚未结束） | `[预约成功, 结束, 取消]` | **即你说的「过了开场但没结束」场景**：开场前/前一天已过期剔除，仅剩「结束」仍在未来 → 进微信授权集；空位 **顺带填入「取消」** → 结束提醒照常发 |
| ④ 已结束（防御·正常不可约） | `now ≥ sessionEnd`（场次已结束） | `[预约成功, 取消]` | 时间轴类全部过期，「结束提醒」已无未来触发点、无法订阅/推送，故不在授权集；仅 1 槽 → **顺带填入「取消」**。属防御性档，正常流程几乎不触发 |

**关键原则：结束提醒的适用性只看 `now < sessionEnd`（场次是否还没结束），与「场次是否已开场」无关。** 因此「开场已过、但场次未结束」的迟到预约，结束提醒依然有效并进入授权集（上表 ③）；只有真正 `now ≥ sessionEnd` 的 ④ 档才无可推送的结束提醒。

**填充规则（最大化微信授权覆盖、减少短信）**：
授权集 = `[预约成功]` ∪ `{仍在未来的时间轴提醒}`，若合计 < 3，则依次补入 `取消`（最多填满 3）。
- ①/② 已占满 3 槽 → 取消不进提交弹窗，仍走「通知设置/预约详情」页授权（主入口）。
- ③/④ 有空位 → 取消顺带进提交弹窗一次性拿下，提前锁定微信授权，避免取消时只能走短信。
- 此规则**不改变「提交恒 1 次弹窗」**，且对拒绝授权的用户无任何副作用（短信兜底依旧生效）。

- 上述每档均为 **1 次弹窗、≤3 模板**，满足「不要两次弹窗」。
- **取消提醒**：主入口仍为「我的-通知设置」或「预约详情」页授权；但提交弹窗有空位时（③/④ 档）会顺带申请，以尽可能让三类提醒都走微信、减少短信兜底。

> 该分配**恒为 1 次弹窗**，且保证预约成功一定在微信授权集内（满足 1.4 的「微信优先+弹窗」）。唯一代价：远期单的「结束提醒」在微信侧可能缺失 → 由短信保底覆盖，符合「短信确保触达」总目标。

### 3.3 用户时序
```
点击提交
  → 先弹 1 次微信授权窗（预约成功 + 适用的时间轴提醒，≤3）
  → 调用 createReservation（带授权结果 subs）
       · 免审：即时发 预约成功（微信优先，失败→短信）
       · 需审核：返回「待审核」，审核通过时再发 预约成功
  → 展示「提交成功页」（应用内必达确认，含留座信息）
后续：remindReservation 定时任务按 notifyPlan 发 前一天/开场前/结束（微信优先，失败→短信）
取消时：发 reserveCancel（微信优先，失败→短信）
```

### 3.4 数据模型
`reservations.notifyPlan` 维持 4 键布尔（无需新增 key）：
`{ reserveSuccess:true, dayBefore, reminder, reminderEnd }`
- `reminderEnd` 不再被硬截断置 false；改为**显式决策**（见 4.1）：远期单时保留为 true 但**不进提交弹窗授权集**（靠短信兜底），当天单时进授权集。
- 幂等标记沿用 `dayBeforeNotified / reminded / ended / xxxNotify` 等。

### 3.5 复用现有机制（不重复造轮子）
- **短信保底**：直接复用 `_lib.shouldSkipSms` + `sendSms`，无需新写。
- **审核=预约成功**：`createReservation` 现有审核通过分支已发 `reserveSuccess`，保留。
- **时间轴发送**：`remindReservation` 现有 4 趟 pass + `plannedOf` 门控 + 幂等标记，保留。
- **取消发送**：`createReservation` 取消分支发 `reserveCancel`，保留（补短信兜底）。

### 3.6 短信兜底铁律（明确 · 覆盖全部 5 类）
- **规则**：任何一类通知，只要微信订阅下发未成功（含用户未授权/拒绝导致的 `43101`、字段非法 `47003`、凭证异常 `-501001` 等），且全局短信开关 + 短信项目设置开启，就必须改走短信补发。落库判定即 `_lib.shouldSkipSms`：**仅当微信结果 `ok===true` 才跳过短信，否则必发短信**。
- **覆盖全部 5 类**：预约成功 / 前一天 / 开场前 / 结束 / 取消，无一例外——不存在「未授权就彻底不通知」的空档。
- **「未授权」情形特别说明**：用户若在弹窗拒绝或勾选「总是保持以上选择(拒绝)」，该类微信发送返回 `43101` → `wxRes.ok=false` → **不跳过短信 → 短信必发**。
- **① 远期单的结束提醒**：因不在微信授权集，定时任务尝试微信时同样会得到未授权结果 → 自然落入短信兜底，与「微信优先、失败转短信」统一模型一致。
- **唯一前提**：短信本身需已开启（全局开关 + 项目短信设置），否则无任何通道可达——这是用户自掌的开关，非本机制缺陷。

## 4. 待确认决策点（请逐条回）

### 4.1 ★ 结束提醒在「远期单」的送达方式（最关键）
当前硬截断会**静默丢弃**结束提醒；本方案改为**显式策略**：
- **A（推荐）**：远期单提交弹窗 = `[预约成功, 前一天, 开场前]`；结束提醒**不进微信授权集**，靠 ③短信兜底，并允许用户在设置页补授权。→ 提交恒 1 弹窗，代价最小。
- **B（全微信覆盖）**：远期单分 2 次弹窗，第 1 次 `[预约成功, 前一天, 开场前]`，第 2 次 `[结束]`。→ 微信覆盖最全，但**违反你「不要两次弹窗」的偏好**。

### 4.2 取消提醒授权入口（采纳「设置页为主 + 有空位顺带」）
- 主入口：仍放「通知设置 / 预约详情」页（用户可随时补授权）。
- 提交弹窗顺带：当提交弹窗授权集 < 3（即 ③ 临近/当场单、④ 已过场次档）时，把「取消」填进同一次弹窗。
- 效果：远期单/当天早单（已满 3）取消走设置页；临近/已过场单取消在提交时即锁定微信授权 → 后续取消优先走微信、减少短信。
- 仍保证「提交时恒 1 次弹窗」。

### 4.3 「客户端弹窗提示」的语义（已确认：两层都要 ✅）
两层并存：① 微信订阅**授权弹窗**（申请预约成功模板，必需）；② 应用内「提交成功页」**必达确认弹窗/页**。两者共同构成「预约成功」的客户端提示，与三层送达模型一致。

## 6. 风险与边界
- 微信一次性订阅「用一条消耗一条」，授权槽不因未使用而浪费；拒绝授权仅影响该模板微信送达，短信兜底仍生效。
- 「总是保持以上选择」陷阱：用户若在弹窗勾「不再询问」并选拒绝，该模板被永久拒收（直至微信设置重开）。应对：弹窗前用自定义浮层解释 + 设置页可重授权。
- 审核类项目：预约成功在审核通过时发，提交弹窗仍照常申请预约成功授权（届时直接可用）。

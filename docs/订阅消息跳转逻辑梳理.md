# 微信订阅消息「点击跳转」逻辑与页面导航方案梳理

> 范围：用户收到微信服务通知卡片并点击后，小程序应如何跳转。
> 区分两类入口：① **订阅消息点击**（本文主线）；② **应用内「提醒」收件箱深度跳转**（真正的逐条差异化导航，见末章）。
> 结论先行：当前 8 类订阅消息点击后只落 **3 个页面**，且**全部不携带参数**。差异化深度跳转实际由应用内收件箱承担，而非订阅消息本身。

---

## 一、微信订阅消息跳转机制（前置约束）

1. 落地页由发送时 `subscribeMessage.send` 的 **`page` 字段**决定，支持 `page?query=...` 形式。
2. ⚠️ **tabBar 页面限制**：若 `page` 指向 `tabBar` 配置中的页面，微信打开时只切换 tab，**query 参数被丢弃**，`onLoad(options)` 拿不到任何参数。这是平台硬限制，无法绕过。
3. 模板 `data` 字段只是**展示文案**（卡片上看到的字），**不是导航参数**，不会传到页面。
4. 推论：要实现「点击直达某条预约」，落地页必须是**非 tabBar 页面**。

本仓库 `tabBar`（`miniprogram/app.json`）：`pages/index/index`（首页）、`pages/mine/mine`（我的预约）。

## 三、差异化导航的真实承担者：应用内「提醒」收件箱

订阅消息只负责「把人拉进小程序」。进入后，**逐条差异化深度跳转由应用内收件箱完成**（这是零成本兜底设计，与推送解耦）：

入口：`pages/admin/hub/hub` 的「提醒」卡 → `pages/admin/inbox/inbox`

- 收件箱列表项点击：`navigateTo /pages/admin/inbox/detail?id=<_id>`
- 详情页主按钮按 `type` 分发（`detail.js:120–125`）：
  - `reviewRes`（预约审核）→ `navigateTo /pages/admin/review/review`
  - `reviewDish`（评论审核）→ `navigateTo /pages/admin/reviewAdmin/reviewAdmin`
  - 其余（new / cancel）→ 「查看该预约」→ `gotoRes` → `navigateTo /pages/admin/view/view?projectId=&date=`
- 顶部「待处理实时计数」快捷入口（`inbox.js:188–195`）：
  - `pendRes > 0` → `/pages/admin/review/review`
  - `pendDish > 0` → `/pages/admin/reviewAdmin/reviewAdmin`

## 四、导航方案建议（改进路线）

### A. 顾客端：保持 `pages/mine/mine`（推荐，改动小）
- tabBar 限制是硬伤，无法带参直达单条预约；且消息语义均为「我的预约」，落列表已足够。
- 若希望「点开直接看到那条预约」：将落地页改为**非 tab 中转页**（如新增 `pages/mine/detail?rid=` 或复用 `pages/result/result?rid=`），中转页读取 `rid` 展示单条并保留「返回我的预约」。⚠️ 此改法会离开 tab 心智模型，建议仅在有明确诉求时做。

### B. 管理员端：在 `page` 上追加 query（推荐优先做，收益大）
落地页均为非 tab，可安全带参。需两处配合：

1. **后端拼接**：在发送处把 `page` 由裸路径改为模板字符串，追加 `?rid=<reservationId>&pid=<projectId>`。
   - `notifyAdmins`（adminNew / adminCancel 走默认 hub）：`page: 'pages/admin/hub/hub?rid=' + rid + '&pid=' + pid`
   - `adminReview`：`page: 'pages/admin/review/review?rid=' + rid`
   - 注意 URL 编码（`encodeURIComponent`）。
2. **前端消费**：
   - `hub.js` `onLoad` 读到 `rid` → 高亮 / 滚动到对应收件箱条目，或自动 `navigateTo` 到 `inbox/detail?id=...`。
   - `review.js` `onLoad` 读到 `rid` → 自动定位并展开该条待审项。

### C. 优先级与风险
- **先做 B**（管理员端带参直达）：改动小、命中「管理员收到消息想立刻处理」的高频场景，且不触碰 tabBar 限制。
- 顾客端 A 属体验优化，非阻塞，按需。
- 任何改动需同步 `cloudfunctions/_lib/index.js`、`createReservation`、`remindReservation`、`cancelReservation`、`reviewReservation` 的发送分支，并 `sync-lib.sh` + 重部署受影响函数。
